# AMENDMENTS - proposed design v1.1 (from VAL-2, 2026-09-28)
Every item verified by grep/run against `abc-bank/backend/` in the zip. Impact: FE = frontend (05-07), T = pytest (08), D = tools+docs (09).

1. **§7.4 example totals.** What: `total_interest 2470.90`, `total_payable 52470.90` (50000.00 @ 9.00 %, 12 months; recomputed with `loan_engine.build_schedule`). Why: v1.0 §7.4 shows 2470.84 / 52470.84 (= EMI x 12) but says "values from §9.4", and §9.4 defines `total_payable = sum(emi_k)`; the last EMI absorbs rounding (11 x 4372.57 + last). The two v1.0 statements contradict; §9.4 wins. `estimate` and `review` both sum the schedule. Impact: FE show API values, never EMI x n (=52470.84). T assert 2470.90 / 52470.90. D fix example.
2. **`AMOUNT_EXCEEDS_LIMIT` never fires alone.** What: rule `amount > 20 x income` always co-occurs with `EMI_TOO_HIGH` (`EMI@9 % / income > 0.50`). Why: tenures are {6,12,18,24,36}; min EMI/P = 3.18 % (36 m); 20 x 3.18 % = 0.636 > 0.50. Impact: FE list both codes; T cannot test it alone, assert the pair; D note.
3. **`LIMIT_EXCEEDED` rule.** Proposal: reserved for *count* limits (today only `POST /accounts`, 5 open accounts, 422). Money min/max (transfer 1.00-200000.00, deposit 1.00-100000.00, loan 5000.00-500000.00) = `VALIDATION_ERROR` 400 with `details.fields`. Why: matches code, no change. v1.0 conflicts with it: §7.3 lists `LIMIT_EXCEEDED` in transfer errors and Appendix B defines it as "Amount/account-count limit"; §5.7 gives the money limits without naming a code. If instead 02/03 should emit `LIMIT_EXCEEDED` for money limits (option b), 02/03 code, FE and T change; recommendation: (a) as above, Appendix B row reworded to "Account-count limit". Impact: FE map 400 to field error; T assert 400 for money limits, 422 `LIMIT_EXCEEDED` for the 6th account; D Appendix B wording.
4. **Interfaces to document (additive).** `failure_sim.resolve_mode(override=None)`: call once per request, pass the concrete mode to `move_money(simulate_failure=)` and `maybe_drop_response(override)` (`RANDOM` would re-roll per hook; a concrete override never touches the DB). `failure_sim.MODES` = NONE, BEFORE_DEBIT, AFTER_DEBIT, BEFORE_COMMIT, DROP_RESPONSE, RANDOM. `transfer_service._run(user_id, key, mode, ctx, work)` -> `(txn_ref, replay)`; `ctx` = `record_failed_txn` kwargs. `health_service.health_summary(check_integrity=True)` (dashboard passes False). Impact: T mock/patch these names; D interface table.
5. **Same key + different body, same user.** Today replays the original (§8.8 literal, no compare). Another user's key -> 400 `VALIDATION_ERROR` "idempotency_key already used". Options: (a) accept as is; (b) new code, e.g. `IDEMPOTENCY_KEY_MISMATCH` 409 (needs Appendix B row + request hashing). Impact: (b) touches 02/03 code, FE, T. Recommendation: (a) for v1.1.
6. **Repay lock order.** v1.0 §9.7 says loan -> accounts -> pick installment; §8.3 lists loan -> original txn -> accounts. Code picks and locks the installment before `move_money`. Extend §8.3: repay = loan row -> next PENDING `repayment_schedule` row (`FOR UPDATE`) -> accounts. accept = loan -> accounts. reverse = original `transactions` row (`FOR UPDATE OF t`) -> accounts. Safe: the loan lock serialises repays. Impact: D; T concurrency tests unchanged.
7. **`db` behaviour.** `run_transaction(retries=3)` = 3 total attempts, sleeps 0.05 s, 0.10 s (v1.0 §8.7 lists 0.05/0.10/0.20 with `retries=3`; code reads `retries` as total attempts, so 0.20 never happens), only on MySQL 1213/1205, then 503 `TXN_RETRY_EXHAUSTED`. `get_connection()` retries `PoolError` for up to 30 s (pool 32; connector pool is non-blocking); after that `PoolError` -> 500. Impact: D; T no pool-exhaustion test needed.
8. **Simulation source.** `accept` uses only the global mode (`resolve_mode(None)`); `repay` also honours body `simulate_failure`; transfer/deposit/reverse validate it against `MODES` (400). Note: `repay` does not validate the value; an unknown string acts as NONE. Impact: FE send `simulate_failure` only on repay; T test accept via `PUT /system/simulation`.
9. **`INTERNAL_ERROR` FAILED rows.** Transfers (`_record_failure`) and loan accept/repay (`_money_op`) write `failure_code=INTERNAL_ERROR` for unexpected exceptions, with `failure_reason = str(e)`. Risk: raw DB text reaches history and the `TRANSFER_FAILED` notification message. Proposal: fixed text "Unexpected internal error" (needs 02+03 change). Impact: T never assert the reason text; FE show `failure_reason` as is.
10. **`current_step`.** v1.0 §6 leaves "everything is filled" open for step 4. Code: 5 if status != DRAFT; else 2 if no details, 3 if no income or < 3 documents, else 4. The guarantor does not move it. Impact: FE wizard resume; T.
11. **Grep gate.** "Balance UPDATE only in `ledger.py` / `init_db.py`" must exclude `tests/` and `selfcheck_*.py` (`selfcheck_api` corrupts balances on purpose for I2/I5). Impact: D, T.
12. **Selfchecks.** They reset the DB: run sequentially, order db -> txn -> loans -> api, never with pytest. `selfcheck_txn` and `selfcheck_loans` need the server on :5000 (HTTP via `requests`); `selfcheck_db` and `selfcheck_api` run in-process (Flask test client, MySQL only). `backend/README.md` says "the last three need the server": wrong for `selfcheck_api`. Impact: D fix README wording (not touched by VAL-2).
